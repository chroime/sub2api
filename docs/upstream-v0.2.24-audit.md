# v0.2.24 合并后功能审计与修复

日期：2026-11-21（Asia/Shanghai）。审计基线为 `54111adf6aa3e9b22aada150f0e29efa94ffbe36`；比较本地合并前 `70fa1732a`、上游父提交 `5c2982a81`、合并提交 `90b1644d9` 及后续页面调整 `9711e1de7`。

## 为什么会出现功能失效

本次确认的问题分布在服务装配、页面重写、请求兼容校验和镜像打包几个环节。之前的局部回归及编译没有覆盖这些环节组合后的完整行为。

余额预扣故障的直接原因是：合并前生成的装配代码直接使用数据库计费仓储；重新生成后启用了已有的合并结算包装层。包装层实现了基础计费接口，却没有透传运行时通过类型断言取得的预扣、恢复、对账和归档接口。因此代码能够编译，但开启预扣后请求会在访问上游之前返回计费 503。该问题已先由 `54111adf6` 修复并在 15 的 Grok 普通、流式请求和监测记录中验证。

另外，模型 ID 复制在后续页面重写中被移除；更新脚本及发布镜像存在更早的打包差异；图片 Key 的目录误报也是已有前端处理缺陷。这些问题的来源分别核对，不能全部归因于同一次文本合并。

## 已确认的问题及修复

| 问题 | 触发与影响 | 修复和证据 |
| --- | --- | --- |
| 余额预扣接口在合并结算包装后不可见 | 开启预扣时，正常 Key 在准入阶段返回 `billing_service_error` | 计费提供器保留完整持久化预扣能力；双网关准入、退款、维护、对账及普通合并结算回归通过；已在 15 验证 Grok HTTP 200 和监测成功记录 |
| 广场模型 ID 一键复制缺失 | `9711e1de7` 重写表格后，上游新增的复制入口消失 | 在当前实际使用的厂商表格中恢复紧凑复制按钮；全部分组与指定分组回归先失败后通过 |
| 合法自定义 metadata 键被误判冲突 | `TraceID` 与 `traceid` 等不同键导致 HTTP/WS 请求被拒绝 | 自定义 metadata 键按精确名称比较；真实重复键、结构化字段及保留的 `user_id` 别名冲突仍被拒绝；扫描器和入口回归通过 |
| 停机清理未等待合并结算通道 | 活跃账单尚未完成时，应用清理即可返回并继续关闭数据库 | 在源装配与生成装配中接入通道 `Stop`；行为回归证明修复前提前返回、修复后等待账单完成 |
| 通用更新可能换成缺少能力的镜像 | 更新脚本选用 `deploy/Dockerfile`，缺少浏览器助手和 PostgreSQL 客户端 | 默认改用根 Dockerfile；保留浏览器授权及应用内备份/恢复工具；更新脚本回归通过 |
| GoReleaser 镜像缺少浏览器运行时 | 发布镜像没有 Node、Chromium、Xvfb、助手文件及环境路径 | 补齐镜像、构建上下文和两份直接发布配置；支持显式精简选项；真实上下文测试与镜像能力检查通过 |
| 图片专用 Key 被误报目录获取失败 | 有效目录返回图片模型，但过滤后的文本列表为空，随后抛出通用获取错误 | 保留完整展示目录，同时保留独立的文本配置候选；“使用”窗口展示图片模型及能力说明；不生成不兼容文本配置；空目录、真实请求失败、混合目录和过期请求分别验证 |
