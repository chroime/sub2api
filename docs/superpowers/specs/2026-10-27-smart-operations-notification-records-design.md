# 智能运维用户余额通知记录设计

## 目标和范围

在“智能运维 → 通知记录”中查询发给平台用户的余额不足邮件，事件限定为 `balance.low`。管理员能够查看通知对应的用户、实际收件人、触发时余额、提醒阈值、发送时间、发送结果、失败原因和完整邮件正文。

记录范围按通知内容确定，包含两种触发方式：

- 自动提醒：用户请求实际扣费后，余额首次跌破有效阈值触发的邮件。
- 手动批量提醒：管理员在用户管理中选择“余额提醒”模板，发给平台用户的邮件。

上游余额和恢复通知、管理员账号额度告警、分组变更、AstrBot、分组与倍率更新邮件、充值成功邮件不属于本功能。

延续已经确认的要求：记录保留 90 天；保存完整收件人、主题和正文，允许管理员查看；第一版提供只读查询。

## 现有链路与接入方式

自动提醒由 `BalanceNotifyService.CheckBalanceAfterDeduction` 判断：扣费前余额大于等于阈值，扣费后余额低于阈值。收件人优先使用已验证且启用的额外通知邮箱，没有时使用用户注册邮箱。

自动提醒通过 `NotificationEmailService` 发送 `balance.low` 模板，并沿用现有用户、收件人和 UTC 日期组合的去重标记。模板或配置错误时，现有逻辑可能改用内置邮件正文；SMTP 传输错误时不会立即发送备用邮件。

手动批量余额提醒通过 `UserBulkEmailService` 检查用户状态、接收偏好、当前余额和有效阈值，然后发送同一个 `balance.low` 事件。每次明确的管理员批量发送仍视为独立操作，保留现有批量结果返回方式。

新增专用的用户余额通知记录服务，接入上述两条路径。记录服务负责持久化和查询，邮件发送仍由现有服务执行。记录写入异常时记录结构化日志，并继续原有发送和计费流程。

## 数据模型

新增表 `user_balance_notification_records`。每行代表一次余额通知处理中的一个实际收件目标；同一用户通知多个邮箱时分别记录。

| 字段 | 说明 |
| --- | --- |
| `id` | 自增主键 |
| `notification_id` | 本次通知处理标识，用于将模板发送和备用正文发送关联到同一通知 |
| `trigger_type` | `automatic` 或 `manual_batch` |
| `batch_id` | 手动批量发送的任务标识，自动提醒为空 |
| `user_id` | 平台用户 ID |
| `user_email`、`user_name` | 触发时的用户账号和名称快照，区别于实际收件人 |
| `recipient` | 实际收件邮箱；没有可用收件人时为空 |
| `balance`、`threshold` | 触发时余额和实际采用的金额阈值 |
| `subject`、`body` | 实际邮件主题和完整 HTML 正文 |
| `status` | `pending`、`sending`、`sent`、`failed`、`suppressed` |
| `suppression_reason` | 退订、重复保护、无有效邮箱等跳过原因 |
| `attempts` | 实际 SMTP 尝试次数，跳过或渲染失败时为 0 |
| `last_attempt_at`、`sent_at` | 最近一次 SMTP 尝试时间和接受时间 |
| `last_error` | 实际失败原因 |
| `delivery_key` | 原有去重键的关联值，仅供排查 |
| `created_at`、`updated_at` | 创建时间和最后状态更新时间 |
| `expires_at` | 创建时间加 90 天 |

索引覆盖创建时间、到期时间、用户 ID、状态和触发方式筛选。`notification_id, recipient` 唯一约束保证同一次通知的状态更新不会创建重复记录。

`delivery_key` 不作为新表的唯一约束，避免重复保护记录覆盖原来的成功记录。发送去重仍以原有设置标记为准。用户改名或删除后，记录保留用户快照，直到自身到期。

若在正文渲染前被跳过，或模板无法渲染，正文可以为空，详情明确显示“未生成邮件正文”，不使用示例模板冒充实际邮件。备用正文实际发送后，记录保存最终使用的正文和发送结果。

## 记录与发送流程

1. 自动扣费达到既有触发条件，或管理员明确提交批量余额提醒时，生成本次通知标识。每个目标邮箱有独立记录。
2. 记录用户账号、余额、有效金额阈值和触发方式。批量操作同时关联批次标识。
3. 接收偏好或原有去重规则阻止发送时，保存 `suppressed` 和具体原因，不执行 SMTP。
4. 成功渲染邮件后保存完整主题和正文，进入 `sending`；真正调用 SMTP 时才增加 `attempts`。
5. SMTP 接受后记录 `sent` 和 `sent_at`。传输失败记录 `failed` 和错误原因。
6. 模板或配置失败触发内置正文发送时，沿用同一通知标识，汇总实际 SMTP 次数和最终结果。SMTP 已接受但去重标记保存失败时，保留发送成功事实，另外记录持久化错误日志。

当前余额通知没有持久化自动重试队列，本功能也不新增重试调度。`failed` 代表本次发送失败，不能显示为“等待自动重试”。进程中断导致没有最终结果的记录保留最后已确认状态，并展示“结果未确认”，不能推断为成功。

只对明确进入余额通知处理的操作保存记录。未跌破阈值的普通请求、配置开关关闭、模板预览和未提交的批量选择不生成发送记录。批量提交后因用户退订、无有效邮箱、余额未低于阈值而跳过的目标显示具体跳过原因。

## 智能运维页面与接口

入口使用“智能运维 → 通知记录”，路由为 `/admin/upstream-governance/notifications`，页面标题为“用户余额通知”。无需选择上游站点。

筛选项：时间范围、发送状态、触发方式、用户 ID、用户账号和实际收件邮箱。默认查询最近 90 天，并按创建时间倒序分页。

列表展示：

- 通知时间、用户账号和实际收件人；
- 触发时余额与有效阈值；
- 自动提醒或手动批量提醒；
- 发送状态、SMTP 尝试次数、最近发送时间；
- 失败或跳过原因，以及查看详情入口。

详情展示完整主题、正文、用户和收件人快照、批次、处理时间及错误信息。完整正文按需请求，列表响应不携带大段 HTML。邮件预览使用禁用脚本的隔离 iframe，并禁止自动加载外部资源或提交表单。

页面使用现有智能运维组件和中文状态文字，时间统一展示为北京时间。移动端采用纵向记录卡片。状态统计随当前筛选条件计算，包含总数、待处理、已发送、失败和已跳过。

新增管理员只读接口：

- `GET /api/v1/admin/upstream-governance/notifications`：返回用户余额通知列表、分页和统计。
- `GET /api/v1/admin/upstream-governance/notifications/:id`：返回单条用户余额通知详情和正文。

接口复用现有管理员权限校验。`sent` 在页面显示“已发送”，并注明它表示 SMTP 接受邮件，收件箱最终送达没有回执证明。

## 保留与兼容

记录从功能启用后开始产生。既有哈希发送标记不能恢复用户、收件人和正文，不据此补造历史发送记录。

记录保留期限为创建后 90 天。查询接口过滤已经过期的记录，后台任务按批次清理 `expires_at <= now` 的数据。清理只涉及本功能的新表。

余额提醒的全局开关、有效阈值、注册邮箱回退、用户退订、UTC 日期去重、模板、备用正文和发送方式继续沿用现有规则。旧的发送标记继续保留。

## 验证与交付

后端验证：

- 自动跌破阈值后的注册邮箱发送、额外邮箱发送和多收件人记录。
- 手动批量余额提醒的成功、失败、退订、无效邮箱和余额未达阈值结果。
- 完整主题、实际正文、余额、有效阈值和用户快照持久化。
- 日期去重跳过不覆盖历史成功记录，备用正文使用同一通知标识。
- SMTP 接受、SMTP 失败、去重标记保存失败和进程中断的状态含义。
- 记录写入失败仍执行原有发送；其他通知类型不进入余额通知记录。
- 管理员权限、参数校验、分页筛选、统计和 90 天清理。

前端验证：智能运维导航、余额通知列表、筛选分页、状态和跳过原因、完整正文详情、北京时间格式、移动端和空状态。

交付包括设计、数据库迁移、两条用户余额通知发送路径接入、管理员查询接口及智能运维页面。采用合成用户和模拟 SMTP 验证，不向真实用户额外发送测试通知。
