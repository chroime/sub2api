# 智能运维统一通知发送记录设计

## 目标

在智能运维中提供统一的通知发送记录，覆盖以下五类通知：

- 用户余额不足
- 上游余额低和余额恢复
- 上游账号额度告警
- 上游分组、描述和倍率变更
- 管理员批量邮件

记录页面需要回答“什么事件、通过什么渠道、发给谁、当前状态、尝试了几次、最近一次错误是什么、正文是什么”。发送记录保留 90 天。现有阈值、收件人、去重、冷却和重试行为保持不变。

## 已确认的产品边界

- 入口位于“智能运维”，提供一个全局“通知记录”选项卡，不要求先选择上游。
- 默认查询最近 90 天，并支持时间、来源类型、事件、渠道、状态、上游、用户、账号和收件人筛选。
- 记录正文完整保存并允许管理员查看。收件人也按完整值保存。
- 状态包括 `pending`、`sending`、`sent`、`failed`、`suppressed`。
- `sent` 表示 SMTP 或目标接口接受请求，不代表收件箱最终送达。
- 第一版只读，不提供删除或手动重发按钮。失败重试沿用现有后台机制。
- 记录写入失败只记录日志，不阻断原有通知发送、计费或调度主链路。
- 90 天清理只删除统一记录，不删除现有业务状态、去重标记或上游余额状态。

## 现有能力和兼容策略

上游分组变更已经使用 `upstream_governance_change_notifications` 持久化投递队列，包含收件人、主题、正文、状态、尝试次数、下一次重试时间、成功时间和最后错误。这个队列继续作为可靠发送和重试的来源，新增统一记录作为跨来源查询入口。

用户余额和账号额度目前通过 `NotificationEmailService` 使用设置仓库中的哈希去重标记。统一记录不会替换这些标记。正常发送路径先检查既有去重规则，再创建或更新统一记录；如果统一记录写入失败，继续按旧逻辑发送。

上游余额监控通过 `balance_monitor_state` 保存低余额状态、最近尝试、最近成功、失败和按收件人的重试预约。统一记录从该发送路径补齐事件和投递信息；现有状态字段继续用于余额卡片和重试判断。

批量邮件当前返回每个收件人的发送结果，但结果没有长期保存。统一记录为每个批量任务的每个收件人创建独立记录，保留现有接口返回行为。

## 数据模型

新增表 `smart_operations_notification_records`，每行表示一个逻辑事件通过一个渠道发送给一个目标。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 自增主键 |
| `source_type` | `user_balance`、`upstream_balance`、`account_quota`、`group_change`、`bulk_email` |
| `source_id` | 来源对象或任务标识 |
| `site_id` | 可选的上游站点 ID |
| `user_id` | 可选的平台用户 ID |
| `account_id` | 可选的上游账号 ID |
| `event` | 例如 `balance.low`、`balance.recovered`、`group.rate_change` |
| `channel` | `email` 或 `astrbot` |
| `recipient` | 完整收件人或目标引用 |
| `subject` | 通知主题 |
| `body` | 完整通知正文 |
| `status` | `pending`、`sending`、`sent`、`failed`、`suppressed` |
| `suppression_reason` | 被抑制时的原因，例如退订、重复、无收件人 |
| `attempts` | 已尝试次数 |
| `next_attempt_at` | 下一次重试时间 |
| `sent_at` | 最近一次成功发送时间 |
| `last_error` | 最近一次失败原因 |
| `dedup_key` | 逻辑事件去重键 |
| `created_at` | 创建时间 |
| `expires_at` | 创建时间加 90 天 |
| `updated_at` | 最后状态更新时间 |

索引包括：

- `created_at DESC`，支持时间线分页；
- `(status, next_attempt_at)`，支持状态统计和待处理查询；
- `(source_type, event, created_at DESC)`，支持来源和事件筛选；
- `site_id`、`user_id`、`account_id`，支持对象筛选；
- `dedup_key, channel, recipient` 唯一约束，防止并发重复记录。

正文和错误字段使用现有邮件正文大小校验，并拒绝包含凭据、会话令牌和 SMTP 密钥的运行时变量。现有上游变更队列的正文仍保留，因为它是重试所需的发送载荷。

## 发送流程

### 用户余额

扣费后检测到余额首次跌破阈值时，创建 `user_balance / balance.low` 记录。若用户退订、触发既有日期去重、没有可用收件人或邮件被既有策略抑制，创建 `suppressed` 记录并填写原因。正常路径继续调用现有 `NotificationEmailService`；SMTP 成功更新为 `sent`，模板、配置或传输失败更新为 `failed`，现有 fallback 行为不变。

### 上游余额

上游成功采集到新鲜余额快照后，低于或等于阈值时创建 `upstream_balance / balance.low`，恢复到阈值以上时创建 `upstream_balance / balance.recovered`。每个站点和收件人独立记录，沿用现有冷却时间、15 分钟失败重试、恢复待发送和进程重启恢复逻辑。`balance_monitor_state` 仍然是调度判断的来源，统一记录是审计查询来源。

### 账号额度

账号日、周或总额度跨过配置阈值时，创建 `account_quota / account.quota_alert` 记录。现有管理员收件人和每日 `ReminderKey` 去重继续生效。发送成功或失败后更新统一记录。

### 分组和倍率变更

现有上游变更队列入队时同步创建或关联统一记录，队列状态变化同步到统一记录。一个逻辑变更对应每个收件人一条记录。基线记录仍然静默，不生成发送记录；重复事件继续由现有 `dedup_key` 唯一约束抑制。

### 批量邮件

批量邮件任务为每个目标用户和收件人创建记录，保存所选模板事件、主题、正文、发送结果和错误原因。接口继续等待每个 SMTP 尝试并返回当前结果；统一记录提供后续审计，不改变批量操作的返回结构。

### AstrBot

现有 AstrBot 目标使用 `qq:<UMO>` 目标引用。统一记录的 `channel` 为 `astrbot`，`recipient` 保存 QQ 群 UMO 引用，正文保存实际推送文本，状态由现有目标接口响应更新。邮件和 AstrBot 分开记录，不共享收件人格式。

## 管理员页面和接口

在智能运维导航新增“通知记录”选项卡，建议路由为 `/admin/upstream-governance/notifications`。

页面包含：

- 总记录数、待处理、已发送、失败、已抑制统计卡片；
- 时间范围筛选，默认最近 90 天；
- 来源类型、事件、渠道、状态筛选；
- 上游、用户、账号和收件人搜索；
- 分页列表；
- 记录展开详情，查看完整主题、正文、目标、尝试次数、下一次重试、成功时间和错误原因；
- 刷新按钮和状态更新时间。

首版不提供记录删除和手动重发。页面采用现有智能运维的卡片、表格、状态徽章和时间格式，移动端改为纵向记录卡片。

新增管理员接口：

- `GET /api/v1/admin/upstream-governance/notifications`：分页和筛选列表；
- `GET /api/v1/admin/upstream-governance/notifications/:id`：完整正文和技术详情；
- 不新增发送接口，避免页面操作绕过现有去重和重试策略。

响应只允许管理员访问。完整正文在管理员权限范围内展示，接口不返回 SMTP 配置、API 密钥、会话令牌或其他凭据。

## 清理和错误处理

新增智能运维清理任务，每次删除 `expires_at <= now` 的记录，按批次处理并记录清理数量。清理失败不影响发送队列和业务请求，下一次周期继续处理。

统一记录写入遵循 fail-open：

- 记录创建失败时记录结构化日志，继续原有发送；
- 发送成功但状态更新失败时，保留现有发送结果并记录错误，后续由状态修复或队列扫描补偿；
- 记录状态为 `failed` 时不代表最终放弃，是否重试由原有队列决定；
- `sent` 只表示目标接口接受请求，不承诺收件箱投递。

## 测试计划

后端测试覆盖：

- 迁移、字段约束、索引和唯一去重；
- 五类来源的记录创建和状态更新；
- 成功、失败、抑制、重复和重试；
- 现有上游变更队列与统一记录同步；
- 正文和敏感字段校验；
- 90 天清理和分页筛选；
- 统一记录写入失败时原有发送仍继续。

前端测试覆盖：

- 智能运维导航和通知记录路由；
- 筛选、分页、统计卡片和刷新；
- 五类来源、五种状态和邮件/AstrBot 渠道展示；
- 正文展开、失败原因、重试时间和空状态；
- 移动端布局和管理员权限错误。

上线验证：先执行数据库迁移，再启动服务，检查五类通知各生成一条记录；核对上游余额卡片的最近发送时间与记录列表一致；确认旧的去重标记、上游状态和失败重试行为没有改变。
