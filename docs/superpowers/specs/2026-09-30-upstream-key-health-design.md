# 上游托管密钥健康与导入防陈旧设计

## 目标

治理中心区分本地已保存密钥与上游实际可见密钥。分组目录采集成功后，独立核验托管密钥；导入和快捷创建账户前复核要复用的旧密钥。上游明确删除密钥后及时告警并暂停受影响的本地账户调度，同时保留密钥、绑定与审计记录。

## 信任边界

- 上游密钥的存在性仅由同一站点、同一已验证上游用户的**完整只读列表**证明。依据是远端数值 ID 与分组 ID；密钥显示名和本地 `has_key` 均不能证明存在。清单分页缺失、用户身份变化、列表失败、上游暂时不可用或权限不支持均为“无法核验”，不推进缺失计数。
- 不使用 `EnsureKey` 核验：它在找不到匹配密钥时可以发创建请求。核验过程不创建、不删除、不泄露密钥明文，不触发推理请求。
- 对于可见但上游不返回完整值的密钥，仅证明 ID/分组仍存在，不能声称已验证明文有效。后续可另设计低成本可选探测。

## 状态与时序

每个已完成托管密钥持久化 `unknown | present | suspected_missing | confirmed_missing | group_changed` 状态、最近成功核验时间、连续缺失次数、首次缺失时间、下一次复核时间和有限错误码。状态与 `has_key` 分开；密钥密文与远端 ID 原样保留。

定时采集保存目录后，使用独立的有界时间执行一次全站密钥清单核验（不是每组一请求）。首次完整缺失时标记疑似，并计划 60 秒后复核。第二次独立的完整缺失确认删除；单次成功重新出现清除缺失计数，但仅恢复本治理中心为“密钥失效”而暂停、且身份仍匹配的账户。站点原有采集间隔保持不变。失败只更新核验错误，不把成功的目录采集改成失败，也不清除已确认的缺失。

确认缺失后，在站点锁下以账户身份、绑定 marker、账号状态的乐观前置条件暂停本地账号调度，记录去重事件并使用系统发件配置通知管理员。暂停原因需区分“分组缺失”和“密钥缺失”；分组存在不能单独恢复因密钥缺失暂停的账号。通知失败独立记录并延迟重试，不重复执行暂停或创建密钥。

## 导入与修复

`CreateKeys` 和 `Apply` 在存在已完成托管密钥或旧绑定密文时，先请求一次完整清单并检查上游用户、ID 和分组。找不到则返回明确的逐项 `upstream_key_missing`，不写本地新账号、不把旧密钥标为复用；清单不可核验时返回 `upstream_key_unverifiable`，不尝试创建新密钥。已有冻结预览重放须尊重最新核验状态，不能把旧成功结果当作新的远端有效证据。

密钥恢复或轮换不是“再点创建”：已完成密钥的存储 CAS 故意拒绝静默覆盖。单独的显式修复流程必须先建立新密钥的持久创建计划，按平台幂等能力创建并复核，再以账号和绑定身份 CAS 切换本地密钥，最后确认新托管记录；任何阶段不确定时展示待确认状态并保留旧值，不能自动重复 POST。

## 管理界面与验收

管理员可在托管密钥列表看到“本地已保存”和“远端状态”两列、最近核验时间和受影响账号，支持一次只读的立即核验。左侧上游列表和运行记录可展示异常数量和确认缺失/恢复事件。普通用户界面不显示治理状态。

合成测试覆盖完整/不完整密钥列表、身份不匹配、首次缺失、60 秒复核、第二次缺失暂停、重复任务幂等、恢复、人工编辑冲突、分组缺失与密钥缺失同时发生、导入旧密钥阻断、跨实例锁与邮件失败。真实 XenoAI 账号只在用户明确进行验收时操作；实现测试不访问真实上游。
