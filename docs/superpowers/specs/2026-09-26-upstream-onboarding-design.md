# Native upstream onboarding and bulk import

The user clarified the approved built-in governance implementation: enter an upstream URL, username and password in the governance center; the center logs in and automatically collects visible groups, rates, prices and account balance. Administrators can create/reveal group keys and map all selected visible groups to a chosen local group with a single preview and apply.

The existing native API connectors remain the execution path. A unified UI orchestrates detection, site creation, password connection and immediate collection. Platform and name are detected from public upstream settings; explicit platform/proxy overrides remain advanced options. Once a site has been created, retries reuse it instead of creating duplicates. CAPTCHA/TOTP challenges are a distinct incomplete state, never successful onboarding. Cross-origin Turnstile cannot be solved merely by reusing its site key on our origin; require the upstream proof when it enforces that check, retain advanced continuation without claiming credentials-only success. Passwords remain transient, cleared on close/success, never logged or stored.

Snapshots gain a nullable account summary: upstream user ID, username/email, balance, frozen balance, used balance/quota, original unit and source. Missing values stay unknown. New API quota is shown in its native unit unless public conversion metadata proves a monetary conversion. Sub2API discovery supplements channels with authenticated model-plaza data, intersected strictly with bindable group IDs; storefront-only groups must not become importable. Preserve complex pricing metadata and label multiplier versus token/request prices independently.

Group key operations are independent of local import. A new encrypted key store records one managed key for each site, remote group and inference transport, with the same stable marker used for imports. Listing reveals metadata only; create/reveal endpoints return plaintext keys with no-store response headers and admin authorization. The administrator page automatically reads and displays complete keys; password, CAPTCHA and session input fields also display plaintext, as the user expressly requested. Persisted encryption is independent of this display choice. Batch results are per item. Repeating creation reuses/reconciles the existing remote key. Imports reuse these keys and older binding keys. Creating keys never creates local accounts or changes local groups.

The catalog provides select-all, compatible target-group assignment and per-row overrides. Known transports are inferred; Grok uses its documented OpenAI-compatible gateway. Unknown/composite groups require an explicit transport choice. No incompatible group is silently dropped. All visible groups can be selected; unsupported/missing choices are shown and block preview until resolved. Show current upstream rates/prices and local sale rates before committing. Existing immutable previews and transactional import behavior remain in force.

Validation uses synthetic upstream servers for native password/challenge flows, authenticated profile/plaza collection, safe key lifecycle and partial retry, plus frontend browser interactions against the locally running build. Real upstream calls happen only through governance backend/UI; external scraping or session import is not evidence of native password login. Back up the isolated app database and binary before the new migration/restart. Do not deploy or merge as part of this change.
