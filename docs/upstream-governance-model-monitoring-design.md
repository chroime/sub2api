# 上游治理中心：管理员模型监测方案

日期：2026-09-27。状态：核心模型监测已实现，包含手动并发批次、独立定时策略、糖果/鹈鹕原题、Token 核对、指定长度的多位置上下文验证、管理员历史与通知。自动阶梯上下文扫描、自动处置生产账户以及可配置保留期仍属于扩展设计。实现与使用说明见 `docs/upstream-governance-model-monitoring.md`。

## 目标与入口

在治理中心增加独立的「模型监测」页签，回答四个管理问题：这个分组的某个模型能否稳定调用、响应是否变慢、能力是否下降、token 统计与可用上下文是否符合预期。监测直接使用对应上游分组的托管 Key，支持导入本地账户前先检测，以及导入后长期定时检测。

当前入口为站点「模型监测」页签，按托管分组 Key 配置目标；「分组与导入」中批量添加监测目标保留为后续扩展。管理员选择模型、请求协议、思考等级和测试模板，预览每轮请求数与最大输入/输出额度后启用。能力模板采用用户指定的「糖果逻辑题」和「鹈鹕骑自行车」，可以单独选择，也可以一起运行。首次发现的模型默认进入待配置列表，不自动开启全量付费测试。既有明确启用的策略后续由后台持续运行，不依赖管理页面打开。

模型候选优先使用该分组采集到的可见模型；上游目录未提供模型时允许管理员手工填写，不能把空目录解释成没有模型。可选的模型列表读取使用对应分组 Key，并显示来源与采集时间；列表可见仅表示候选，不等于已验证可调用。尚无托管 Key 时，沿用治理现有的分组 Key 创建与回显流程，由管理员在添加目标时明确完成授权；后台调度不自行创建新 Key。

目标身份为 `站点 ID + 上游分组 ID + 推理协议 + API 模式 + 请求模型名`。绑定 ID 可空；名称用于展示，Key 用托管记录 ID 引用。请求使用固定目标，不经过本地账户池或自动回退路由，避免检测到另一个渠道。上游平台自身是否切换模型无法由客户端完全控制。

### 模型与思考等级

模型选择与思考等级是两个独立控件。思考等级提供「低 / low」「中 / medium」「高 / high」三档，支持「单档运行」和「三档对比」：前者只请求所选档位，后者对同一模型、同一原始题目分别发起三次独立请求。两道模板同时选择时，单档每轮 2 次请求，三档每轮 6 次请求；重复采样再按次数相乘。运行前展示支持的档位、实际请求数与额度预估。

参数由「平台 + API 模式 + 模型」能力表映射。OpenAI Chat Completions 使用该模型支持的 `reasoning_effort`，Responses 使用该模型支持的 `reasoning.effort`；Anthropic、Gemini 及其他兼容平台按具体模型的原生 effort/thinking 参数接入，不能把所有模型都视为支持相同字段或三档。若只能设置 thinking token budget，需有明确、可见且版本化的档位映射；没有可靠对应关系的档位标为不支持，不凭空把 low/medium/high 换成任意 token 数。

记录请求档位、实际发送字段、适配器版本及上游响应。模型或接口拒绝指定档位时标为「思考等级不支持」；能力未知则标为「未验证」，不能静默丢弃参数、改用默认档位或混入其他档位样本。接口接受字段只表示请求被接受，不能证明上游实际执行了对应推理强度。三档对比遇到不支持的档位时，明确显示该档未执行及原因。

每个「目标 + 模板版本 + 思考等级 + 其他请求参数」分别建立基线，三档只在对比视图并列展示，不能共用同一条能力或延迟趋势。题干原文完整保存，不为思考档位额外添加限制性提示词；费用预算、超时、输出额度和真实平台能力属于策略设置，界面独立展示，不注入题目文本。对于平台不支持的参数，管理员可明确改配置后新建一次运行，保留原失败记录。

## 检测指标与判定

| 类别 | 记录与展示 | 判定边界 |
| --- | --- | --- |
| 可用性 | 请求完成、有效文本、流结束状态、错误分类、近期成功率和样本数 | HTTP 200、心跳帧或 role 帧不代表推理成功；跳过和预算暂停不记为渠道失败 |
| 响应延迟 | 首个有效文本时间 TTFT、总耗时、输出阶段耗时、吞吐量，按相同配置统计 p50/p95 | 首字节与首个有效文本分开；非流式不提供 TTFT，不能用总耗时代替；没有足够输出样本时吞吐量为未知 |
| 糖果逻辑题（智商测试） | 数值结论、取法、最优性解释、复核状态、不同思考等级下的结果与耗时 | 结果正确与证明完整分开记录；单道已知题不能代表通用 IQ，也不能证明真实模型身份或参数量 |
| 鹈鹕动画测试 | 原始 HTML、隔离动画预览、下载、人工评价与三档作品对比 | 生成成功、视觉效果与动作协调分开判断；不以出现 `<svg>` 或代码长度自动计算智力分数 |
| Token 核对 | 上游声明的输入/输出/缓存/推理 token，本地可复核文本的 token 估算、字符数及 UTF-8 字节数 | 隐藏推理、服务端提示词和实际内部 tokenizer 无法直接测量；缺失 usage 为未知，不填 0 |
| 实测上下文 | 各长度的多位置检索结果、已验证长度、失败位置与失败类型 | 接口接受长文本不等于模型利用了全部文本；验证到 64K 表示「至少在本次测试中通过 64K」，不是证明上限就是 64K |

### 糖果逻辑题模板

发送给被测模型的原始中文题目如下，题干和数量保持用户提供的内容；标准答案与判分说明保存在评测配置中，不发送给被测模型。

```text
在一个黑色的袋子里放有三种口味的糖果，每种糖果有两种不同的形状（圆形和五角星形，不同的形状靠手感可以分辨）。现已知不同口味的糖和不同形状的数量统计如下表。参赛者需要在活动前决定摸出的糖果数目，那么，最少取出多少个糖果才能保证手中同时拥有不同形状的苹果味和桃子味的糖？（同时手中有圆形苹果味匹配五角星桃子味糖果，或者有圆形桃子味匹配五角星苹果味糖果都满足要求）
苹果味 桃子味 西瓜味
圆形 7 9 8
五角星形 7 6 4
```

同一数量表在管理员详情中按列展示：

| 形状 | 苹果味 | 桃子味 | 西瓜味 |
| --- | ---: | ---: | ---: |
| 圆形 | 7 | 9 | 8 |
| 五角星形 | 7 | 6 | 4 |

**标准结论为 21 颗，固定取 9 颗圆形和 12 颗五角星形。** 前提是使用题目给出的触感信息选择形状，不能在摸取前辨认口味，取出后不放回。参赛前确定总数不妨碍事先确定这两类形状各取多少颗。

上界证明：圆形西瓜只有 8 颗，取 9 颗圆形必有苹果或桃子；五角星形非苹果只有 `6 + 4 = 10` 颗，非桃子只有 `7 + 4 = 11` 颗，因此取 12 颗五角星形必同时有苹果和桃子。圆形中的苹果可配五角星形桃子，圆形中的桃子可配五角星形苹果，必有合适组合。

下界证明：考虑每种形状按以下合法的最不利次序取出。

```text
圆形：西瓜 × 8 → 苹果 × 7 → 桃子 × 9
五角星形：西瓜 × 4 → 苹果 × 7 → 桃子 × 6
```

在这个次序下，「圆形苹果 + 五角星形桃子」至少需要圆形 9 颗加五角星形 12 颗，共 21 颗；「圆形桃子 + 五角星形苹果」至少需要圆形 16 颗加五角星形 5 颗，也共 21 颗。因此任何 20 颗的取法都可能失败。这个下界还覆盖看见已取出的口味后自适应选择下一颗形状的策略；选择顺序不能越过这两个总数下界。

如果另加「不能按形状选择、只能完全盲取」的条件，才是 29 颗。盲取失败集合分别最多为：仅圆形西瓜加任意五角星形 `8 + 17 = 25`、任意圆形加仅五角星形西瓜 `24 + 4 = 28`、两类均无苹果 `17 + 10 = 27`、两类均无桃子 `15 + 11 = 26`。最多 28 颗仍可失败，所以该不同题意下需 29。模型可讨论此分支，但不能把 29 作为允许按触感选择形状的原题最优答案。

结果记录分成「数值结论」「可行取法」「最优性解释」「题意辨析」与「复核状态」。清楚且唯一的最终数值结论可以与 21 比较；不能仅因全文出现 `21` 就判正确。无法可靠识别结论、同时列出多个答案而未区分条件时标为待人工复核，不强制被测模型改用 JSON 或固定回答格式。仅回答 21 可以记录数值正确，但不能由此判定说明或最优性证明完整。解释是否有效由管理员查看原文并复核，记录评价人和评价版本；不能声称程序可以确定性校验任意自然语言证明。

这个固定题目适合观察同一配置是否稳定答对、思考等级是否改变解释与耗时。单道公开题存在记忆或缓存影响，不能据此宣布模型通用 IQ、真实身份或全面能力。原题不自动添加随机标记或改写数字；如以后增加变体，应作为另一个明确版本的模板，独立保存答案和基线。

### 鹈鹕骑自行车模板

发送给被测模型的原始提示词完整保留为：

```text
创建一个 HTML，内容是 SVG 绘制一个鹈鹕骑自行车的 2D 动画，你不需要任何测试，不要有任何限制
```

不附加代码风格、测试框架、lint、结构化输出或生成内容限制，不自动重写、修补、格式化作品，也不把通过自动测试作为交付条件。模板中的「你不需要任何测试，不要有任何限制」是给被测模型的题目内容；治理系统仍使用管理员明确设置的请求额度、超时和真实平台参数能力，这些配置不改写提示词。

完整保留原始回答，并提供原文查看与下载。若回答是完整 HTML，直接保存该内容作为作品；若包含 Markdown 代码围栏或说明文字，原始回答保持原样，另外提供来源明确的 HTML 代码块提取预览，保留字节内容并允许管理员选择代码块。无法确定作品入口时显示原文和待选择状态，不自动猜测并改写 HTML。下载分别提供「原始回答」与「HTML 作品」，不会用预览包装替换原件。

管理员详情提供可播放的隔离 iframe 预览和 low/medium/high 并列作品对比，支持重新播放或重新加载。预览环境允许作品所需的本地 SVG/CSS/脚本动画，但使用独立隔离源或不带 `allow-same-origin` 的 sandbox iframe，禁止访问管理员凭据、父页面、顶层导航和弹窗；网络连接和外部资源按隔离预览策略控制，不给作品注入管理 Token。隔离策略通过预览容器或响应头实施，不修改原始作品。外部依赖被隔离环境阻止时明确显示「预览环境不支持该依赖」，不能当作模型智力下降，也不能在管理员主页面直接执行生成内容。

人工评价分项为「能否辨认鹈鹕与自行车」「2D SVG 画面表达」「是否存在持续动画」「脚踏、腿部与车轮动作协调」「视觉完整度」。每项可记录符合、部分符合、不符合、未评价及文字备注；管理员看到真实动画后评价，不从 `<svg>` 字符串、代码量或静态截图推导动画质量，更不据此产生伪精确的智商分数。未评价作品保留待评价状态，可长期生成和归档，但不自动触发视觉能力下降告警。

### 模板版本与长期比较

两道模板各有独立版本及原始提示词哈希，模型参数、temperature、思考等级、输出预算和适配器版本保存为运行快照。请求失败、输出截断、参数不支持、答案错误和待人工复核分开记录；超时不会自动成为逻辑题答错，作品在隔离环境无法加载也不会自动成为视觉质量不合格。跨模板、版本、思考等级和请求参数的结果不拼成一个总分。

糖果题建议用前三次完整且已确认的结果建立初始参考，展示答案稳定性和同配置的延迟分布；基线连续正确后出现连续两次已确认错误可触发逻辑题退化通知，规则允许调整。自然语言解释与动画表现只对已人工评价的同版本样本比较，待评价不填 0 分，不因缺少评价触发能力告警。初版不凭单次答案或作品自动停用生产账户。

### Token 与上下文

「token 实际大小」同时覆盖计数核对和有效上下文两个含义：

1. **计数核对**：固定可复现输入，记录请求中的可见文本和返回的可见文本。tokenizer 支持且口径已知时计算本地估算值，并记录 tokenizer 名称/版本、是否含消息包装；不支持则只展示字符/字节数。上游 usage 原值分别保留，不把缓存、推理 token 或不同计费口径相加比较。只有比较口径一致时才提供差异比例，否则显示「不可直接比较」。
2. **上下文验证**：用程序生成随机背景材料，在多个位置嵌入随机问答对或标记，按 4K、16K、32K、64K 等阶梯增加负载，分别检验前部、中部、尾部与跨段信息。标明长度的 tokenizer 估算来源，同时记录字节数。测试出现明确超限、截断、接受但检索错误、超时或预算不足时停止或按策略降阶复验，不自动无限放大。

上下文测试默认手动或低频执行，每级多次采样后展示通过率；相同材料长度下同时保留对照样本，避免把某一次推理失败断言为上下文截断。模型声明的上下文长度可作参考字段，与实测结果并列展示。

## 页面结构

「模型监测」页头只放健康目标数、待关注目标数、执行中任务和今日测试用量。支持按站点、分组、模型、协议和异常类型筛选。

列表主列为「上游分组名称 / 模型 / 协议」，随后显示思考等级、当前状态、最近 TTFT、糖果题结论或作品评价状态、最近检测时间与下一次计划。token 核对、上下文长度和完整延迟分位数放入详情抽屉，避免主表过宽。名称优先，ID 作为次要信息。

详情分为「可用性与速度」「糖果逻辑题」「鹈鹕动画」「Token 与上下文」「运行记录」。逻辑题同时展示原文回答、标准答案、解释复核与三档对比；动画页展示原始作品、可播放预览、下载和人工评价。复用渠道状态的时间矩阵和趋势图交互，清楚区分未检测、正常、异常、取消、数据过期及样本不足。窗口提供 24 小时、7 天、30 天，所有时间沿用 `YYYY-MM-DD HH:mm:ss`。

提供批量套用模板、立即执行、暂停/恢复、查看任务和取消执行。管理员能够查看题目、返回结果、判分依据与原始 usage，但默认列表不显示长文本；响应正文仅在详情按需加载。导出能力仍受管理员权限控制。

## 长期调度与用量控制

建议模板默认值如下；间隔允许自由填写正整数分钟，与治理中心现有规则一致。

| 模板 | 建议周期 | 每轮范围 |
| --- | --- | --- |
| 轻量探活与延迟 | 15 分钟 | 1 次带随机验证的短文本流式请求 |
| 糖果逻辑题 | 1440 分钟 | 原题 1 次；单档或 low/medium/high 三档，三档为 3 次请求 |
| 鹈鹕骑自行车 | 手动，或管理员选择低频周期 | 原提示词生成 HTML/SVG 动画；单档 1 次、三档 3 次请求，作品归档后人工评价 |
| Token 计数核对 | 1440 分钟 | 明确可见文本口径的固定测试 |
| 长上下文验证 | 手动，或管理员选择低频周期 | 受预算限制的阶梯测试 |

新建策略默认关闭，保存配置与启用执行分开。管理员明确启用后，正常周期执行无需重复确认。每次配置变化显示新的预计请求数量；实测费用以 usage 和采集时的价格快照估算，不用整个站点的余额差推算测试费用，因为生产请求会同时消耗余额。

新增独立持久化任务队列，按分钟扫描到期策略，使用唯一 `(policy_id, scheduled_at, revision)` 防止同一计划批次重复排队。批次内每次实际请求再以 `(run_id, template_version, reasoning_effort, sample_index)` 标识；三档是三个不同子任务，不能因共用计划槽而相互覆盖或漏跑。同一目标的各档子任务依次执行，遵守同目标不重叠约束。短事务内预留预算并领取租约，离开站点锁后执行网络请求；全局并发、每站并发分别约束。长任务支持租约续期和管理员取消。

配置包含单次输入/输出限制、每日请求数、每日 token 预算、可选费用预算和输出字节上限。第一期以请求数、输入/输出字节和协议可控的输出额度作为可验证的硬约束。只有 tokenizer/消息包装口径、隐藏推理额度、输出上限及价格均可确定时，才把 token/费用预算作为硬约束；缺少这些前提时只能显示估算，或按管理员要求的硬预算暂停，不能保证实际上游账单不超额。

对可计算的预算，执行前按单次上界原子预留，结束后用可观察数据结算；usage 缺失或结果未知时保留保守预留。并发任务不能各自通过余额检查后一起超额运行。价格未知且费用预算为执行前提时暂停并提示缺少价格；管理员可明确选择仅按可验证的请求数/字节/输出额度运行，界面须显示当前实际生效的预算类型。

进程重启只接续下一次有效计划，不补跑全部历史周期。已经发送但结果未知的收费请求标为 `indeterminate`，不盲目重发。租约过期不代表请求一定未执行；重试策略需要区分排队阶段、请求未发出、已发送未确认三个阶段。取消任务也不能保证上游立即停止计费。

Key 或策略版本变化、站点换地址/账户、目标分组消失时，取消或暂停对应任务，运行结果标明旧配置，不能混入新基线。新分组不会自动继承旧名称相似分组的策略。采集失败与分组删除分开判断。

## 告警

复用系统 SMTP 发件配置和管理员收件人解析，新增模型监测专属 incident 与通知状态。告警类型包括连续调用失败、恢复、TTFT 持续恶化、能力基准下降、相同口径下 token 差异持续异常、上下文验证退化及任务预算耗尽。

默认建议连续 3 次轻量探活失败才告警、连续 2 次成功后发恢复通知；延迟至少有 5 个有效样本才比较。糖果题按同模板、同思考等级、同参数的已确认结论判断连续退化；解释和动画作品的待评价状态不进入自动能力告警。条件与通知冷却可配置，同一事件合并通知，发送失败在治理界面显示。测试失败和邮件投递失败分别记录。初版只告警；后续若接入自动暂停账户，必须设置独立开关、连续确认与恢复条件。

## 架构与复用边界

现有治理探测位于 `backend/internal/upstreamgovernance/connector_probe.go`，只发送 `Reply OK.`、最多 8 token 的非流式请求，验证非空文本，记录总耗时。它可以保留为兼容轻量检查，不能直接提供能力、真实 TTFT 或 token 核对。

现有渠道检查器 `backend/internal/service/channel_monitor_checker.go` 使用简易随机算术挑战；流式响应先整体读取再解析，无法用于准确的首内容计时。现有 v2 渠道指标来自 `usage_logs` / `ops_error_logs`，治理评测不得混入这些生产数据。

推荐新增治理模型 runner 和协议适配层，覆盖 OpenAI Chat Completions、Responses、Anthropic Messages、Gemini streaming；兼容厂商按现有治理协议映射接入。Responses-only 模型可明确选择 Responses，协议不支持应显示为协议不兼容，不能据此认定所有调用都不可用，也不能静默换协议后合并样本。

网络请求复用 `backend/internal/service/upstream_governance.go` 的站点客户端工厂，保留显式代理、地址规则和禁止重定向。新增 runner 单独控制首内容超时、流式空闲超时、总超时与最大响应大小；增量消费流并在第一个有效文本事件到达时记录时间，不等待整个响应后再计算 TTFT。

当前治理循环一次最多 20 个到期站点、每站最多 5 个检查，单轮约 50 秒，且站点锁覆盖远程操作。能力评测、动画生成和长上下文不能加入这条执行循环，否则会占住采集、导入和余额检测。新 worker 使用独立队列和运行租约；仅在读取站点/Key 修订快照时短暂取锁，调用期间不持有站点治理锁。

图表可复用 `frontend/src/features/channel-monitor-v2/MonitorTrendChart.vue`、`RelayPulseMatrix.vue` 的展示结构或抽取通用图层，另写治理数据适配。不要向它们的现有接口伪造生产渠道统计数据。

## 数据与管理员权限

建议采用独立表（名称为设计建议，迁移编号待实施时分配）：

| 表 | 主要内容 |
| --- | --- |
| `upstream_governance_model_targets` | 站点、分组、模型、协议、托管 Key 引用、可选本地绑定、配置修订 |
| `upstream_governance_monitor_policies` | 原始模板/版本、单档或三档选择、周期、采样与超时、预算、启停与告警条件 |
| `upstream_governance_model_runs` | 唯一计划槽、对比批次与各档子任务、实际参数快照、租约、阶段、用量与预算预留、结果摘要 |
| `upstream_governance_model_case_results` | 原始输入/输出与 HTML 作品引用、数值结论、解释复核、人工视觉评价及评价人/版本、时延、usage、本地估算器与错误类型 |
| `upstream_governance_model_rollups` | 同配置维度的按小时/日统计与保留期 |
| `upstream_governance_model_incidents` | 故障/退化/恢复事件及按收件人的投递与冷却状态 |

预算计数和预留必须有持久化原子记录，不能依赖内存计数。原始题目/响应建议保留 7 天、逐次摘要 30 天、小时统计 90 天、日统计 365 天，均可配置；清理不删除仍被运行中任务、未结算预算或事件引用的数据。

所有接口统一位于 `/api/v1/admin/upstream-governance/`，包括目标列表、立即检测、队列、取消、历史、导出和实时进度；沿用现有管理员中间件。普通用户和未登录用户直接访问结果 ID 也不能读取。前端路由和菜单再做管理员限制，但权限不能只靠隐藏入口。

现有渠道 `ListUserView` 会读取 enabled 的 `channel_monitors`；所以不把治理任务写入该表，也不把结果写入用户可见的渠道缓存、聚合或调用日志。独立表、独立 API、独立聚合确保默认私有。作业正文不会记录管理登录密码或 API Key，凭据始终引用治理已有的托管记录。

## 实施顺序与验收

**第一期：监测底座。** 管理员权限、目标与托管 Key 引用、持久化队列及预算、手动/定时流式检测、TTFT/总时长/上游 usage、私有历史矩阵、异常与恢复邮件。旧轻量检查保留兼容，迁移不会自动启用已有站点的新任务。

启用新策略前检查同一站点/分组/协议/模型对应的旧 `Binding.ProbeEnabled` 计划，界面展示现有周期并提供「接管原定时检测」选项。管理员明确接管时，在同一事务内启用新计划并停用旧计划，保留旧历史；第一期不允许同目标两套调度同时启用，避免重叠请求与新预算之外的额外调用。单次手动检测也经过同目标运行锁及本次预算检查。后续如支持并行计划，需先统一预算和调度归属。

**第二期：指定基准与思考等级。** 模型选择、low/medium/high 能力映射、单档和三档对比、糖果原题及标准答案、数值结论与解释复核分离、鹈鹕原提示词与原始 HTML 保存/下载/隔离动画预览/人工评价。按同配置建立基线并支持已确认答案的退化通知，同时增加 tokenizer 适配与计数口径说明。计数缺失或不可比较时明确展示未知；不要求生成作品通过代码改写、lint 或自动测试。

**第三期：上下文与横向比较。** 分级长上下文、同题库同参数跨渠道对比、可选生产账户处置。先建立可靠历史，再决定是否让模型监测影响调度。

治理功能验收必须覆盖管理员之外无法读取所有入口；直接使用对应分组 Key；SSE 心跳/空帧不计 TTFT；正常流结束与中途断开可区分；缺失 usage 不变成零；预算并发不超额；重启/取消/租约丢失不盲目重复收费；慢测试不阻塞采集与导入；分组、Key、思考等级或策略修订不混入旧基线；样本不足不会触发能力下降；合成请求不进入用户渠道状态。另需确认原始提示词与作品不被改写、不支持的 reasoning 字段不被静默丢弃、21 的数值结论不被等同于证明完整、29 的盲取分支不会误判为原题最优、未人工评价的动画不产生自动质量分、预览无法访问管理员凭据。协议 fixture 和模拟时钟用于验证治理系统本身，不作为对鹈鹕生成作品新增测试要求；真实上游仅在管理员选定目标并启用后调用。
