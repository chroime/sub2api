# Codex 门票增强功能运维说明

入口为管理后台「系统设置 → 扩展功能」，包含「Codex 292 · 官方 0.2.6」「Codex 332 · 导入版本」和下方的「Codex 门票动态」。两个模式分别配置、分别保存，使用独立的票据和采集状态。账号按 `292`、`332` 或 `off` 选择模式；保存一个模式不会启用另一个模式。

两个全局开关默认关闭；已有管理员配置继续生效。本次增强沿用原生 HTTP、WebSocket、ACK、预扣费和计费链路，业务请求使用已获取的有效票据，后台负责采集。

## 采集配置

| 选项 | 默认值与范围 | 行为 |
| --- | --- | --- |
| 采集后复验 | 默认关闭，292/332 分别设置 | 开启后，捕获票据还需携票发起一次额外请求；捕获与复验使用同一代理，均须成功完成并返回所请求的模型。会增加采集请求量和耗时。 |
| 采集代理池 | 每个模式最多选择 32 个不同代理 | 从「IP 管理」选择。停用、过期或已不存在的代理会跳过；优先复用成功路线，失败后在后续尝试中轮换。 |
| 采集并发 | 默认 3，整数范围 1～16 | 每个模式独立限制后台采集任务；账号、分组和业务请求仍使用原有并发设置。 |

原有独立采集代理配置继续可用，代理池作为补充路线。采集使用专门配置的路线，日常业务仍使用账号自己的代理。

292 关闭复验时保留仅读取响应头的采集方式。332 无论是否开启额外复验，都要求完整、成功的 SSE 响应，并核对实际返回模型。模型名称一致只代表通过协议校验，不代表对回答质量作出保证。

## 旧票据、凭据变化与失败退避

票据现在绑定访问令牌和 ChatGPT 账号身份。旧记录若缺少 `credential_hash`，保留记录但不再用于转发，必须等待后台重新获取。新票据也会检查格式和内嵌签发时间；重复读到旧票不会延长其有效期。

- **401/403：** 暂停当前凭据的采集。正式请求发生鉴权失败时，只撤销该请求实际使用的票据；晚到的失败不会删除后来写入的新票。
- **凭据更新：** 令牌或 ChatGPT 账号身份改变后建立新的采集状态，原凭据的鉴权暂停和冷却不会继承。新凭据需要获取自己的票据。
- **429：** 保留仍然有效的票据，进一步采集至少退避 **5 分钟**，并遵循更长的 `Retry-After` 或重置时间提示。界面没有绕过退避的立即重试操作。
- **网络、采集或复验失败：** 延后尝试；有其他可用采集代理时，后续尝试可以切换路线。

无有效票时继续按该模式原有的 fail-open/fail-closed 配置处理业务请求。

## 查看运行状态

「Codex 门票动态」显示**当前服务实例**的状态和近期事件，可按模式、账号筛选，查看代理名称、失败原因、到期时间和下一次尝试时间。

页面可见时约每 **5 秒**自动刷新，也支持手动刷新；隐藏页面或离开此页会暂停轮询。刷新失败会保留上一次成功显示的数据。每个实例最多保留 **300 条近期事件**和 **2048 条最新状态**，这是有界运行记录；多实例部署时须按所连接的实例查看，进程重启后会重新积累。

管理员接口为 `GET /api/v1/admin/settings/codex-tickets/monitor`。返回内容包含状态摘要，不包含原始票据、凭据哈希、授权头或代理地址及密码。

## 后续手工验证

以下步骤供管理员日后在测试环境执行；本次实现使用本地 mock 验证，**未发起真实试采，也未启用现场开关**。

1. 打开「扩展功能」，确认两个模式当前开关与已保存配置。刷新页面，核对采集并发默认值、复验开关和代理选择能正确回显。
2. 在「IP 管理」准备可用的测试代理，为测试账号明确选择一个模式。为该模式选择采集路线，先保持复验关闭、使用默认并发，单独保存。
3. 需要实际联调时，由管理员手动启用所选模式。在「门票动态」观察采集和保存结果；出现可用票后，再用该测试账号执行正常业务请求并检查调用结果及使用次数。
4. 需要验证复验时，再开启该模式的复验，观察后续采集的复验事件及实际返回模型校验。复验开关只影响后续采集，不会立即重新验证已有票据。
5. 通过本地 mock 验证 401/403、429 和凭据更新：检查鉴权暂停、至少五分钟的下次采集时间、有效票保留，以及新凭据重新获取票据的行为。
6. 切换浏览器标签页或离开设置页，确认监控轮询暂停；返回后确认能够恢复刷新。按测试前记录恢复测试环境配置。
